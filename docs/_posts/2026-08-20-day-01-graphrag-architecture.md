## 시작: "RAG를 어떻게 만들 것인가?"

3개월 전, GraphRAG 서비스를 처음 설계할 때 나는 막혔다.

> "검색만 잘하면 되지 않나? 왜 이렇게 복잡해야 해?"

당시 Task였던 것:
- ITSM 시스템의 서비스 요청(SR) 데이터로 챗봇을 지원
- 사용자 질의에 정확하고 근거 있는 답변 제공
- 3개 채널(ITSM, 챗봇, AICC)에 최적화된 형식으로 반환

단순하게 생각했다. **"검색 → LLM → 답변"** 이면 될 거라고.

하지만 첫 MVP를 만들고 테스트했을 때 문제가 터졌다.

## 문제 1: "검색만으로는 안 된다"

초기 설계:
```
사용자 질의 → PostgreSQL 검색 → Azure LLM → 답변
```

결과: **정확도 23%** 😱

원인 분석:
- 단순 키워드 검색으로는 유사 사례를 못 찾음
- "환불 지연" 질의가 "결제 오류" 관련 SR을 놓침
- LLM에 충분한 맥락이 없어서 환각 생성

**깨달음**: 검색은 단순히 "후보를 찾는" 단계가 아니라, "올바른 근거를 제공하는" 단계라는 것.

## 문제 2: "하나의 검색 방식으로는 부족하다"

두 번째 시도:
```
PostgreSQL (정확한 매칭) +
Neo4j 벡터 (의미론적 유사성) +
Azure Search (하이브리드)
= 다중 제공자 통합
```

그런데 이들을 어떻게 통합할 것인가?

- 각 제공자가 다른 스코어를 반환 (0~1 사이, 하지만 스케일이 다름)
- 단순히 평균내면 안 됨 (한 제공자가 우점)
- 중복 결과를 어떻게 제거할 것인가?

**해결책**: RRF (Reciprocal Rank Fusion) 도입
```python
# RRF = 1/(rank+60) 를 모든 제공자에서 계산해 합산
# 스코어 정규화 문제 해결
score = sum(1/(rank_pg + 60) + 1/(rank_neo4j + 60) + 1/(rank_azure + 60))
```

## 문제 3: "근거는 어디서 나올 것인가?"

LLM이 정확한 답변을 생성해도, **"이 답변이 어디서 나왔는가?"** 라는 증명이 없었다.

- Citation이 필수 (규제 요건)
- 하지만 LLM이 생성한 citation이 정확하지 않을 수 있음
- "근거 없는 사실 주장" = 위험

이 문제를 푸려면 LLM 이후 **검증 단계**가 필요했다.

**새로운 구조 탄생:**
```
질의
 ↓
[라우팅] - 5가지 의도 분류
 ↓
[검색] - 다중 제공자 (PostgreSQL + Neo4j + Azure)
 ↓
[경로] - 근거 경로 찾기 (Neo4j 그래프 탐색)
 ↓
[컨텍스트] - 그래프 정보를 LLM 입력으로 변환
 ↓
[생성] - Azure OpenAI로 답변 생성
 ↓
[검증] - Citation이 근거에 있는가? (Grounding)
 ↓
[렌더링] - 채널별 형식 변환 (ITSM/챗봇/AICC)
 ↓
답변
```

## 깨달음 1: "아키텍처는 문제 해결의 시각화"

이 7단계 구조는 "좋은 설계"여서가 아니라, **실제 문제를 해결하기 위한 필연적 선택**이었다.

각 단계가 해결하는 문제:
- **라우팅**: "사용자가 뭘 원하는가?" 
- **검색**: "관련된 정보는 뭔가?"
- **경로**: "왜 이 정보가 관련 있는가?"
- **컨텍스트**: "LLM이 이해할 형태로 어떻게 제시할 것인가?"
- **생성**: "정확한 답변을 만들 수 있는가?"
- **검증**: "이 답변이 사실인가?"
- **렌더링**: "사용자가 이해할 형태로 어떻게 제시할 것인가?"

문제가 없으면 단계도 필요 없다. 

우리는 "멋진 아키텍처"를 만든 게 아니라, **"문제들을 해결하다 보니 이 구조가 나왔다"**.

## 깨달음 2: "스택 선택은 문제 유형을 따른다"

왜 이 기술들인가?

| 문제 | 기술 | 이유 |
|------|------|------|
| 정확한 ID 조회 | PostgreSQL | 관계형 + ACID |
| 의미론적 유사성 | Neo4j 벡터 | 그래프 + 벡터 인덱스 |
| 경로 탐색 | Neo4j Cypher | 관계 중심 + 패턴 매칭 |
| 구조화 검증 | Python 타입 | 즉각적 피드백 |
| LLM 연동 | Azure OpenAI | 기업용 + 안정성 |

선택은 **"이게 가장 멋진 기술이라서"**가 아니라, **"이 문제를 가장 간결하게 푸는 기술이라서"**였다.

## 첫 번째 마일스톤: Mock 테스트 통과

초기 설계 완료 후, Mock 데이터로 테스트했다.

**결과: 617개 테스트 100% 통과** ✅

하지만 이건 속임수였다. Mock 데이터는 너무 깔끔했기 때문이다.

## 이 여정에서 배운 것

**1. 아키텍처는 현재 문제에 맞춰진다**
- 은탄환은 없다
- 문제가 먼저고, 구조는 나중이다
- 설계할 때 자신의 가정을 쓰라. 나중에 그것을 검증할 수 있다

**2. 복잡성은 문제에서 나온다**
- "이게 필요해?"라고 묻자
- 필요하면 그 이유를 알 수 있다
- 그 이유가 가장 좋은 문서다

**3. 다음은 실제 데이터다**
- Mock은 신뢰를 주지 못한다
- 실제 데이터로 이 구조가 작동하는지 확인해야 한다
- 그때가 진짜 시험이다
