그래프 경로를 LLM이 읽을 문장으로 바꾸는 얘기를 정리했다.

증상은 전부 다른데 **원인의 모양이 같았다.**

> 테스트는 통과했다. 다만 테스트가 검증한 대상이
> **실제 시스템이 아니라 내가 짠 코드 자신**이었다.

오늘 저녁에 잡은 네 건 모두 이 문장으로 요약된다.
그래서 개별 버그보다 이 패턴을 중심으로 정리한다.

| 번호 | 증상 | 테스트가 못 잡은 이유 |
|---|---|---|
| P0-2 | 실 Neo4j 그래프 탐색이 전부 실패 | 가짜 드라이버가 어댑터에 맞춰져 있었다 |
| P0-4 | 존재할 수 없는 ID로 그래프를 탐 | Mock 데이터가 실 데이터 형식을 어겼다 |
| P0-6 | 필터로 막은 권한을 문장으로 우회 | 경계 검사와 실제 사용 지점이 달랐다 |
| P0-5 | 비 SR 조회가 항상 "없음" | 더블이 실 그래프에 없는 속성을 갖고 있었다 |

## 1. P0-2: 가짜가 진짜를 따라가면 검증이 아니다

### 증상

실 Neo4j에 붙이면 그래프 확장이 **100% 실패**했다.
로그에는 `GRAPH_QUERY_FAILED`만 찍혀서 "Neo4j가 죽었나" 싶었는데, 실제 원인은 이거였다.

```python
await driver.execute_query(query, ..., timeout_=policy.timeout_ms / 1000)
```

설치된 드라이버(6.2.0)는 **홑밑줄로 끝나는 미지의 키워드 인자를 예약어로 보고**
`ValueError`를 던진다. 즉 쿼리는 서버에 닿아본 적조차 없었다.
그 `ValueError`가 상위에서 제공자 장애로 뭉개지면서 원인이 가려졌다.

멀티홉 데모 경로가 통째로 막혀 있었던 셈이다.

### 왜 테스트는 초록불이었나

여기가 오늘의 핵심이다. 어댑터마다 가짜 드라이버를 따로 들고 있었고,
그 가짜의 시그니처가 하필 이랬다.

```python
async def execute_query(self, query, *, parameters_, database_, timeout_):  # 어댑터에 맞춤
    ...
```

**가짜가 어댑터를 따라가면, 어댑터가 무슨 인자를 넘기든 통과한다.**
테스트는 "어댑터가 어댑터 자신과 일치한다"를 확인하고 있었다. 동어반복이다.

### 고친 방식

```python
# tests/conftest.py — 더블 하나로 통일, 실 드라이버와 같은 규칙 적용
class Neo4jDriverDouble:
    async def execute_query(self, query_, **kwargs):
        for key in kwargs:                      # 홑밑줄 규칙을 더블도 지킨다
            if key.endswith("_") and key not in _KNOWN:
                raise ValueError(...)
        assert isinstance(query_, (str, Query))
```

여기에 **시그니처 대조 테스트**를 붙였다.
더블이 실 드라이버에서 벗어나면 그 테스트가 먼저 깨진다.
반대로 드라이버에서 그 규칙이 사라지면 더블이 없는 제약을 강제하게 되므로,
규칙이 존재하는지도 함께 확인한다.

이건 결국 **더블 자체를 검증 대상으로 올린 것**이다.
Mock을 쓰면 항상 이 위험이 따라온다는 걸 알고는 있었는데,
"프로덕션 계약을 테스트로 고정한다"는 게 이런 형태구나 싶었다.

### 곁가지로 배운 것 둘

**① 타임아웃과 실패는 다른 사건이다**

```python
GRAPH_QUERY_TIMEOUT   # 쿼리는 유효한데 예산을 넘김 → 예산/인덱스 조정
GRAPH_QUERY_FAILED    # 쿼리 자체가 깨짐        → 코드 수정
```

운영 대응이 완전히 다른데 같은 코드로 보고하고 있었다.
관측 가능성이라는 게 로그를 많이 찍는 게 아니라 **구분 가능한 코드를 주는 것**이었다.

**② 드라이버 예외 원문을 옮기면 안 된다**

Neo4j 예외 메시지에는 접속 URI가 그대로 들어 있다.
그게 API 응답이나 로그로 새면 자격증명 노출이다. 회귀 테스트로 고정했다.
예외 체이닝(`raise ... from exc`)은 유지하되 메시지는 옮기지 않는다.

## 2. P0-4: 열린 정규식은 없는 ID를 만들어낸다

ID 파서가 이런 모양이었다.

```python
SR_PATTERN = r"SR[A-Z]?\d[A-Z0-9-]*"   # 접두사 뒤를 열어둠
```

관대해서 좋다고 생각했는데 실 데이터를 전수 조사해보니 반대였다.

```
SR      SRM + 10자리(1,212건) 또는 11자리(6건)
변경    CHG + 10자리, 하이픈 없음 (371건 전수 균일)
장애    INC + 10자리, 하이픈 없음 (267건 전수 균일)
릴리즈  REL + 4자리 + '-' + 2자리 (114건)  ← 하이픈을 쓰는 유일한 유형
답변    RPL + 1~4자리(1,384건) / WN-숫자(3건)
담당자  AGT-{한글이름}
```

원래 계획서에는 "하이픈 포함 CHG·INC 지원"이라고 적혀 있었다.
실측은 **정확히 반대**였다. 하이픈은 릴리즈에만 있다.

### 왜 이게 P0인가

```
검색이 실패한다        → 사용자가 안다
없는 ID로 그래프를 탄다 → 아무도 모른다
```

`CHG2607-11`처럼 존재할 수 없는 문자열이 앵커가 되면,
탐색은 조용히 0건을 주고 시스템은 그걸 "관련 정보 없음"으로 처리한다.
**틀린 전제 위에서 답이 만들어진다.** 실패보다 나쁘다.

자릿수가 어긋나면 앞부분만 잘라 인식하지도 않게 했다.
잘린 ID는 다른 ID가 아니라 없는 ID다.

### 인식은 하되 앵커로 쓰지 않는다

`RPL638`이 오류 코드 패턴(영문 3 + 숫자 3)에 걸려 `ERROR_CODE`로 해석되고 있었다.
`ANSWER_ID` / `EMPLOYEE_ID` 유형을 새로 만들어 오분류를 막되,
`AnchorType`에 대응 값이 없으므로 앵커 해석 단계에서 건너뛴다.

> **인식 ≠ 사용.**
> "무엇인지 안다"와 "그걸로 탐색한다"를 분리할 수 있다는 걸 이번에 알았다.

담당자의 순수 숫자 ID는 의도적으로 뺐다.
자유 문장에서 숫자만으로 담당자를 식별하면 **모든 연도와 건수가 담당자가 된다.**
이 형식은 명시적 필터로만 받는다.

### Mock이 실 데이터를 배신하고 있었다

`mock_graph.json`과 `golden_queries.json`이 `CHG2607-11`을 쓰고 있었다.
실 데이터가 만들어낼 수 없는 값이다.

**Mock이 실 데이터가 생성 불가능한 값을 담고 있으면, 그 테스트는 오프라인 데모만 통과한다.**
P0-2와 완전히 같은 실패 모양이다. 프리징 manifest 해시까지 갱신했다.

## 3. P0-6: 필터로 막은 것을 문장으로 우회할 수 있었다

이건 좀 놀랐다. **권한 상승이 실제로 성립하는 상태**였다.

### 어떻게 성립했나

```
① API 경계: enforce_data_scope 가 "요청 필터"를 검사한다
② 서비스  : _resolved_filters 가 질의에서 뽑은 시스템을 필터에 append 한다
③ 제공자  : 같은 필드의 여러 값은 OR 로 평가된다
```

B2C 권한만 있는 사용자가 필터에 `Navitaire`를 넣으면 403이다.
그런데 **질문 문장에 "NSK"라고 쓰면**, Entity Resolution이 그걸 Navitaire로 정규화해서
필터에 더해버리고, OR로 평가되니 그대로 검색이 나간다.

```
필터  : [B2C]                 ← 인증 통과
질의  : "NSK 장애 알려줘"
결과  : [B2C, Navitaire]      ← OR 평가 → 권한 밖 데이터 노출
```

검사 지점(①)과 실제 사용 지점(②)이 달라서 생긴 구멍이다.
**TOCTOU와 구조가 같다.** 검사한 값과 쓰는 값이 다르면 검사는 의미가 없다.

### 고친 원칙: 더하지 말고 좁혀라

```python
# 인증 범위를 상한으로 서비스까지 전달하고, 질의 추출 범위와 교집합을 계산
effective = auth_scope & extracted if extracted <= auth_scope else auth_scope
```

- 인증 범위는 **상한(ceiling)** 이다. 요청 본문이 아니라 인증 컨텍스트에서만 채워진다.
- 질의에서 뽑은 시스템은 **더하는 게 아니라 좁힌다.**
- 좁히는 쪽이 맞는 이유가 하나 더 있다. 여러 시스템 권한을 가진 사용자가
  특정 시스템을 지목했는데 나머지 결과를 계속 끌고 오면 그건 검색 품질 문제이기도 하다.
  보안 수정이 정확도 수정을 겸했다.

### 403을 줄지 무시할지

여기서 한참 고민했다.

| 경로 | 처리 | 이유 |
|---|---|---|
| 명시적 필터로 범위 밖 지정 | **403** | 의도가 분명하다 |
| 질의 문장의 단순 언급 | **무시 + 경고** | 403은 존재 여부를 알려주는 오라클이 된다 |

문장 언급에 403을 주면, 사용자는 문장을 바꿔가며
**"어떤 시스템이 존재하는지"를 열거할 수 있다.** 오류 응답 자체가 정보 채널이 된다.

그렇다고 조용히 버리지도 않는다. `OUT_OF_SCOPE_ENTITY_IGNORED` 경고를 남긴다.
결과가 왜 좁아졌는지는 호출자가 알아야 한다.

### 마지막에 발견한 누출

검색 필터를 다 막고 나서 디버그 응답을 봤더니 이게 남아 있었다.

```json
"canonical_entities": [{"surface": "NSK", "canonical": "Navitaire"}]
```

필터 우회는 막았는데 **정식 명칭은 친절하게 알려주고 있었다.**
호출자가 자기 범위 밖 시스템을 열거할 수 있다.

> 접근 제어는 데이터 경로에만 있는 게 아니라 **관측 경로에도 있어야 한다.**

낮에 "컨텍스트 조립 단계에도 보안이 필요하다"고 썼는데, 같은 이야기가
디버그 출력에서 한 번 더 나왔다. 검색을 막았다고 끝이 아니었다.

## 4. P0-5: "없다"와 "찾아보지 않았다"는 다르다

`EXACT_LOOKUP`은 유형 이름이 `_ID`로 끝나는 첫 엔터티를 잡아 **SR RDB**로 보냈다.
SR 원장에 변경·릴리즈·장애 레코드는 없다. 그러니 결과는 항상 비어 있다.

사용자에게는 이렇게 보인다.

```
"CHG2607000003 알려줘"  →  "해당 변경 정보가 없습니다"
```

실제로는 **조회한 적이 없다.** 데모에서 CHG·REL·INC를 물어보는 순간 드러나는 경로였다.

### 유형별 원장으로 분리

실측상 셋 다 Neo4j에 전수 존재하고(변경 371 / 릴리즈 114 / 장애 267)
각 키에 RANGE 인덱스와 CONSTRAINT가 있다. 그래프가 사실상의 원장이다.

```
ports/record_lookup.py       비 SR 원장의 단건 조회 계약 (RDB 생기면 구현만 교체)
application/record_lookup.py 유형 → 원장을 명시적으로 맺는 ExactLookupRouter
adapters/neo4j_record_ledger.py  실측 라벨·키 (변경/chg_id, 릴리즈/rel_id, 장애/inc_id)
```

### 이름 모양으로 분기하면 안 된다

P0-4에서 `ANSWER_ID` / `EMPLOYEE_ID`를 추가하면서 `_ID`로 끝나는 유형이 늘었다.
이름 모양으로 고르면 "SRM... 과 RPL638 확인" 같은 질의가
**SR 원장에 답변 ID를 묻게 된다.**

앵커가 될 수 있는 네 유형만 명시적으로 매핑했다.
문자열 모양에 기반한 디스패치는 유형이 늘어나면 반드시 무너진다.

### 없는 ID와 권한 밖 ID는 같은 응답이어야 한다

```
없는 ID       → EMPTY
권한 밖 ID    → EMPTY   (403 아님)
```

응답이 다르면 그 차이 자체가 **ID 존재 여부를 확인하는 수단**이 된다.
P0-6에서 배운 것과 똑같은 논리다. 계약 테스트로 두 응답의 `status`·`grounded`가
같음을 고정했다.

## 5. 그리고 오늘 마지막에 또 당했다

P0-5를 커밋하고 실 Neo4j로 검증하다가 하나 더 나왔다.

접근 필터를 만들 때 "시스템·서비스는 평면 속성이 아니라 관계다"까지는 맞췄다.
그런데 **그 관계가 어느 노드에 붙어 있는지는 확인하지 않고 추측했다.**

2026-08-09 실측:

```
SR              대상시스템 1,246/1,246   대상서비스 1,246/1,246
변경·릴리즈·장애   둘 다 0건
```

노드 자신에게 필터를 걸면 조건이 항상 거짓이라 **모든 레코드가 배제된다.**
P0-6 이후 인증 범위가 요청 필터를 항상 채우므로,
운영에서 비 SR Exact Lookup은 **전부 EMPTY**가 될 참이었다.

단위 테스트는 통과했다. 더블이 레코드에 시스템을 **직접 달아두고 있었기 때문이다.**
오늘만 세 번째다.

귀속 경로를 실 그래프대로 우회하게 바꿨다.

```cypher
변경    (node)<-[:파생]-(SR)
릴리즈  (node)<-[:편성]-(변경)<-[:파생]-(SR)
장애    (node)-[:관련SR]->(SR)      // 281/281 전수 보유
```

함께 정정한 것들.

- `node.description`은 **어느 라벨에도 없다.** DBMS가 매 조회마다 경고를 내고 있었다.
- 본문은 변경에만 있다(`body` 385/385). 릴리즈는 본문 속성이 아예 없고,
  장애는 `cause_detail`(14/281)을 쓴다.

실 Neo4j 검증 결과는 이렇게 나왔다.

```
유형별 조회 3/3 성공 (210~300ms, 터널 경유)
  CHG2607000003 / REL2607-02 / INC2607000011 → systems=['B2C'] services=['결제']
없는 ID → None, 범위 밖 ID → None  (외부 응답 구분 불가)
EXPLAIN: 세 유형 모두 NodeUniqueIndexSeek, 전체 스캔 없음
```

참고로 **그래프가 계속 자라고 있다.** 하루 만에 변경 371 → 385,
릴리즈 114 → 123, 장애 267 → 281.
전수 조사 결과를 상수처럼 믿으면 안 되겠다는 생각이 들었다.
비율(N/N)로 기억하고 절대값은 다시 세는 게 맞다.

## 오늘 저녁의 정리

| 배운 것 | 한 줄 요약 |
|---|---|
| 테스트 더블 | 더블이 구현을 따라가면 테스트는 동어반복이 된다 |
| 계약 고정 | 더블 자체를 실물과 대조하는 테스트가 따로 필요하다 |
| 관대한 파서 | 열린 패턴은 존재할 수 없는 값을 만들어낸다 |
| 인식과 사용 | "무엇인지 안다"와 "그걸로 탐색한다"는 분리 가능하다 |
| 검사 지점 | 검사한 값과 쓰는 값이 다르면 검사는 없는 것과 같다 |
| 범위 결합 | 권한은 더하는 게 아니라 상한으로 두고 교집합을 잡는다 |
| 오류 응답 | 응답이 갈리면 그 차이가 정보 유출 채널이 된다 |
| 관측 경로 | 접근 제어는 debug 출력에도 있어야 한다 |
| 실측 우선 | 관계인지 속성인지, 그리고 그게 어느 노드에 붙었는지까지 |

가장 크게 남은 건 이거다.

> **내가 만든 가짜에게 물어보면 내가 믿고 싶은 답이 나온다.
> 실물에 물어봐야 실물이 답한다.**

앞선 글에서 "GraphRAG의 어려움은 그래프를 타는 게 아니라 결과를 언어로 옮기는 것"이라고 썼는데,
오늘 하나 더 붙었다. 그 앞에 **"실제 그래프가 어떻게 생겼는지 아는 것"** 이 있다.
설계 문서에 적힌 모양과 적재된 모양은 다르고, 다르다는 사실은 테스트가 알려주지 않는다.
