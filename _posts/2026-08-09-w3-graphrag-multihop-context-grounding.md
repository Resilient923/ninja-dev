## 들어가며

오늘 리트리버의 그래프 탐색 계층을 실제 Neo4j에 붙였다.
그런데 **경로를 찾는 데 성공해도 답변이 나오지 않는** 상황을 만났고,
그 원인을 파고들면서 GraphRAG의 구조에 대해 꽤 많이 배웠다.

결론부터 말하면, GraphRAG에서 어려운 부분은 "그래프를 타는 것"이 아니라
**"탄 결과를 LLM이 읽을 수 있는 형태로 바꾸는 것"** 이었다.

---

## 1. GraphRAG 파이프라인을 5단계로 쪼개보기

작업하면서 머릿속에 정리된 구조는 이렇다.

```
① 질문 이해     "이 장애 왜 났지?"
       ↓  Intent Router + ID Parser
② 앵커 찾기      그래프 탐색의 시작점 노드 확정
       ↓
③ 그래프 탐색    관계를 타고 여러 다리를 건넌다
       ↓
④ 컨텍스트 조립  경로를 LLM이 읽을 텍스트로 변환
       ↓
⑤ 답변 + 출처    생성하고, 모든 문장에 근거를 붙인다
```

처음엔 ③이 핵심이라고 생각했다. 실제로는 **④가 병목**이었다.

### Vector RAG와 갈리는 지점

이 구조에서 ③이 없으면 그냥 Vector RAG다.

```
Vector RAG : 질문 → 임베딩 → 유사 문서 K개 → 답변
Graph  RAG : 질문 → 앵커 → 관계 탐색 → 경로 → 답변
```

차이가 극명해지는 질문이 있다.

> "이 장애의 원인이 된 릴리즈는 무엇인가?"

장애 문서와 릴리즈 문서는 **텍스트가 서로 닮지 않았다.**
장애는 증상을 적고, 릴리즈는 배포 내역을 적기 때문이다.
그래서 벡터 유사도로는 절대 연결되지 않는다.

```
장애 ─원인→ 릴리즈 ←편성─ 변경 ←파생─ SR
```

이 관계를 타고 가야만 나온다. 이게 Graph RAG를 쓰는 이유 전부다.

---

## 2. 배운 것 ①: 스키마 이름 하나가 전체를 죽인다

Cypher 템플릿이 참조하는 속성명과 실제 그래프의 속성명이 달랐다.
`change_id`로 조회하는데 그래프에는 `chg_id`로 저장돼 있는 식이다.

무서운 건 **에러가 안 난다**는 것이다.

```cypher
MATCH (c:변경 {change_id: $anchor_id})   // 존재하지 않는 속성
RETURN ...
// → 예외 없음. 그냥 0건.
```

SQL이라면 `column does not exist`로 즉시 터진다.
Cypher는 조용히 빈 결과를 준다. 그리고 상위 계층은
"검색 결과가 없나 보다"라고 판단한다.

### 그래서 배운 것

**추측하지 말고 실제 그래프에 물어봐야 한다.**

```cypher
MATCH (n:변경) WHERE n.change_id IS NOT NULL RETURN count(n)  // 0
MATCH (n:변경) WHERE n.chg_id    IS NOT NULL RETURN count(n)  // 371
```

이렇게 `0/N` vs `N/N` 형태로 전수 확인하니 논쟁의 여지가 없어졌다.
설계 문서에 적힌 이름과 실제 적재된 이름이 다를 수 있다는 걸 전제로 깔아야 한다.

그리고 이런 계약은 **테스트로 고정**해야 한다.

```python
RETIRED_PROPERTIES = ("change_id", "release_id", "incident_id", ...)

def test_templates_do_not_use_properties_absent_from_the_graph():
    for filename in registered_template_files():
        for retired in RETIRED_PROPERTIES:
            assert retired not in statement
```

만든 뒤에 **일부러 옛 이름으로 되돌려서 테스트가 실제로 실패하는지** 확인했다.
실패하지 않는 테스트는 없는 것과 같기 때문이다. (변이 테스트, mutation testing)

## 3. 배운 것 ②: 근거 사슬은 한 칸만 끊겨도 무너진다

이게 오늘 가장 크게 배운 부분이다.

속성명을 다 고쳐서 경로가 정상적으로 나오게 만들었다.
그런데도 답변은 여전히 "근거 부족"으로 끝났다.

원인은 출처 레지스트리를 만드는 이 코드였다.

```python
version = node.properties.get("source_version")
if not version:
    continue          # ← 이 노드를 통째로 건너뜀
```

`source_version`(출처 버전)이 없으면 그 노드를 **출처 목록에서 제외**한다.
그런데 그래프에는 이 속성이 아예 없었다. 결과적으로:

```
경로 탐색 성공
   ↓
모든 노드가 출처 등록에서 탈락
   ↓
답변 문장에 붙일 citation이 0개
   ↓
검증기: "출처 없는 사실 문장" → INSUFFICIENT_EVIDENCE
```

### 그래서 배운 것

RAG에서 **검색 성공 ≠ 답변 가능**이다.

```
검색 → 근거 등록 → 컨텍스트 → 생성 → 출처 검증
```

이 사슬은 **AND 조건**이라 한 칸만 끊겨도 최종 출력이 0이 된다.
그리고 끊긴 지점은 마지막 단계에서야 증상으로 드러나기 때문에,
"검색이 안 되나?" 하고 엉뚱한 데를 파기 쉽다.

디버깅할 때 **단계별로 개수를 세보는 습관**이 중요하다는 걸 체감했다.
경로 N건 → 등록된 출처 M건 → 컨텍스트 블록 K건, 이렇게.

## 4. 배운 것 ③: 관계 이름만 넘기면 LLM은 아무것도 못 한다

원래 컨텍스트 생성 코드는 이랬다.

```python
relations = " → ".join(edge.type for edge in path.edges)
text = f"[PATH:{path_id}] {relations}"
```

출력은 이런 모양이다.

```
[PATH:root-incident:...] 원인 → 편성 → 파생
```

관계 이름만 있다. LLM 입장에서는
**어떤 노드인지, 언제 일어났는지, 어느 방향인지** 하나도 알 수 없다.
이걸 주고 "원인을 설명해줘"라고 하면 지어낼 수밖에 없다.

### 개선한 형태

```
장애 INC-XXXX 「결제 승인 실패」 (발생 2026-07-10 07:01, severity=1등급)
  ─원인→ 릴리즈 REL-XXXX 「정기배포」 (배포 2026-07-09 12:18, status=DEPLOYED)
  ←편성─ 변경 CHG-XXXX 「승인 타임아웃 재시도 로직 수정」 (변경 2026-07-08 01:10)
  ←파생─ SR SR-XXXX 「결제 승인 실패」 (status=RESOLVED)
```

여기에 담은 정보는 네 가지다.

| 요소 | 왜 필요한가 |
|---|---|
| **노드 유형 + ID** | 무엇에 대한 이야기인지, citation을 어디에 걸지 |
| **라벨(제목)** | 의미. `CHG-XXXX`만으로는 LLM이 판단 불가 |
| **시각 정보** | 인과의 핵심. 배포가 장애보다 **먼저**여야 원인일 수 있다 |
| **관계 방향** | 방향이 없으면 인과가 뒤집힌다 |

### 방향 표기가 특히 중요했다

경로를 노드 순서대로 걸으면서, 각 엣지가 정방향인지 역방향인지 판정한다.

```python
arrow = f"─{edge.type}→" if edge.from_id == current_id else f"←{edge.type}─"
```

- `장애 ─원인→ 릴리즈` : 장애가 릴리즈를 원인으로 지목
- `릴리즈 ←편성─ 변경` : 변경이 릴리즈에 편성됨

이걸 전부 `→`로 통일해버리면
"릴리즈가 변경을 유발했다" 같은 **거꾸로 된 인과**가 생성된다.
관계 방향은 그래프에서 공짜로 얻는 정보인데, 렌더링에서 흘리기 쉽다.

### 시각 정보는 분 단위까지만

DB에서 오는 타임스탬프는 `2026-07-10T07:01:00.000000000` 같은 형태다.
나노초까지 넣으면 토큰만 먹고 판단에는 아무 도움이 안 된다.
`2026-07-10 07:01`로 잘라 넣었다.

컨텍스트 길이는 유한한 자원이라, **판단에 기여하지 않는 문자는 전부 비용**이라는 걸
새삼 느꼈다.

## 5. 배운 것 ④: 프롬프트에서 "닮은 것"과 "이어진 것"을 섞으면 안 된다

원래는 모든 컨텍스트를 한 덩어리로 넘겼다.

```
검증된 컨텍스트:
<그래프 경로>
<벡터 검색으로 찾은 유사 사례>
```

문제는 이 둘의 **증거로서의 성격이 완전히 다르다**는 것이다.

| 근거 | 의미 | 인과 진술 가능? |
|---|---|---|
| 그래프 경로 | 관계로 **확인된** 사실 | ✅ 가능 |
| 유사 검색 | 텍스트가 **닮았을 뿐** | ❌ 불가 |

섞어서 주면 LLM이 "닮은 사례"를 근거로 원인을 단정한다.
그래서 절을 나눴다.

```
그래프 인과 경로 (관계로 확인된 사실. 원인 진술은 여기에만 근거할 것):
...

검색된 유사 사례·문서 (내용이 비슷할 뿐 인과관계의 근거는 아님):
...
```

프롬프트에서 **근거의 등급을 명시**하는 것.
RAG 논문들에서 말하는 grounding의 실무적 형태가 이런 거구나 싶었다.

## 6. 배운 것 ⑤: 컨텍스트는 개인정보가 새는 통로다

경로를 렌더링할 때 노드 속성을 그대로 넣으면
내부 URL이나 담당자 실명이 딸려 들어간다.

```
변경 CHG-XXXX (pr_url=https://github.internal/.../pull/42)
담당자 AGT-홍길동
```

이게 그대로 컨텍스트에 들어가면 **LLM이 그것까지 인용한다.**
답변에 내부 URL이 박혀 사용자에게 나가는 것이다.

그래서 두 가지를 넣었다.

```python
_EXCLUDED_KEYS = frozenset({"pr_url", "author", "responsible", ...})

def _mask_person_name(text):   # AGT-홍길동 → AGT-홍**
    return _PERSON_SUFFIX.sub(lambda m: m.group(1) + "**", text)
```

식별자 자체는 citation에 필요해서 남기고, **이름 부분만** 가렸다.

RAG를 만들 때 보안은 검색 필터에만 있는 게 아니라
**컨텍스트 조립 단계에도 있어야 한다**는 걸 배웠다.
검색은 통과시켜도 될 데이터가, 프롬프트에 들어가면 안 되는 경우가 있다.

## 7. 배운 것 ⑥: 라벨 안의 줄바꿈이 구조를 깬다

사소해 보이는데 실제로 겪은 문제다.
답변 본문을 라벨로 쓰는데, 본문에 줄바꿈이 있었다.

```
  ─답변포함→ 답변 RPL-XXX 「요청 취소 처리 안내
취소 처리 완료.」
```

들여쓰기로 홉을 구분하는 구조인데, 줄바꿈 때문에 다음 줄이
**들여쓰기 없는 새로운 홉처럼** 보인다. LLM이 오독하기 딱 좋다.

```python
" ".join(text.split())   # 모든 공백을 한 칸으로 접기
```

구조화된 텍스트를 LLM에 줄 때는
**필드 값이 구조를 깨뜨리지 않도록 정규화**해야 한다.
CSV에서 콤마 이스케이프하는 것과 같은 이야기다.

## 8. 오늘 확인한 사실 하나

작업 중에 좀 뼈아픈 걸 발견했다.

전체 그래프에서 **인과 관계(`원인`)가 단 1건**이었다.
유사 관계는 5,975건, 타임라인은 295건인데.

Root Cause 템플릿 4개가 전부 이 관계에 의존하기 때문에,
**멀티홉 인과 데모가 사실상 한 케이스로만 동작한다**는 뜻이다.

기능을 다 만들어도 **데이터가 없으면 증명할 수 없다.**
GraphRAG는 그래프의 밀도가 곧 시스템의 능력이라는 걸
숫자로 확인한 셈이다. 인제스트 쪽과 확인이 필요한 부분.

## 오늘의 정리

| 배운 것 | 한 줄 요약 |
|---|---|
| 스키마 계약 | Cypher는 틀린 속성명에 에러 대신 0건을 준다 |
| 근거 사슬 | 검색·등록·컨텍스트·생성·검증은 AND 조건이다 |
| 경로 렌더링 | 관계명만으로는 LLM이 인과를 못 만든다 |
| 방향 표기 | 방향을 잃으면 인과가 뒤집힌다 |
| 근거 등급화 | "닮은 것"과 "이어진 것"을 프롬프트에서 분리 |
| 컨텍스트 보안 | 검색 필터만으로 개인정보가 막히지 않는다 |
| 데이터 밀도 | 관계가 없으면 멀티홉은 증명 불가 |

가장 크게 남은 건 이거다.

> **GraphRAG에서 어려운 건 그래프를 타는 게 아니라,
> 탄 결과를 LLM이 이해할 수 있게 만드는 것이다.**

Cypher를 잘 쓰는 것과, 그 결과를 언어로 옮기는 것은 별개의 기술이었다.
