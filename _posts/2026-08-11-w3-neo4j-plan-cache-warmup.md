## 들어가며

지난 글 「Neo4j에서 직접 데이터를 가져오니 발생한 문제들」의 마지막 "다음에 할 것"에
이렇게 적어뒀었다.

> 실 Neo4j에서 정상/타임아웃 쿼리 캡처 + EXPLAIN·PROFILE (사내망 접속 시점)

어제 사내망이 열려서 그 대기열을 소화했다. 캡처하러 들어갔다가 두 건이 나왔고,
둘 다 **데모 첫 질의를 그대로 깨는 종류**였다.

| 건 | 증상 | 실제 원인 |
|---|---|---|
| 플랜 컴파일 | 첫 실행만 `GRAPH_QUERY_TIMEOUT`, 재실행은 통과 | 쿼리가 아니라 쿼리 **준비** 비용 |
| P0-9 잔여 | 유사 사례 답변이 전부 폴백으로 떨어짐 | 근거 유형을 그래프 경로에서**만** 찾음 |

테스트는 280 → 290 → 293으로 늘었다.

## 1. 두 번째부터 되는 버그

`RUN_LIVE_NEO4J=1`로 통합 테스트를 처음 돌리자 플래그십 원인 질의가
`GRAPH_QUERY_TIMEOUT`으로 떨어졌다. 그런데 **같은 명령을 다시 치면 통과한다**(19 passed, 7.5초).

이런 게 제일 안 좋다. 로그만 보면 간헐 장애로 보이고, 간헐 장애로 보이면
"Neo4j VM이 좀 불안한가 보다" 하고 넘어가게 된다.
그런데 재현이 100%였다 — **차가울 때 실패, 따뜻할 때 성공.**

### 먼저 쿼리를 의심했는데 아니었다

원래 하려던 게 PROFILE 캡처였으니 그대로 7개 템플릿을 다 떠봤다.

```
전부 NodeUniqueIndexSeek 로 진입
DbHits 34~293
웜 실행 34~80ms   (예산 1,000ms)
풀스캔 0건
```

느릴 이유가 없다. 예산의 10분의 1도 안 쓴다.
그럼 첫 실행에서 나머지 900ms는 어디로 갔나.

### 캐시를 비우니까 갈렸다

```cypher
CALL db.clearQueryCaches()
```

이걸 넣고 다시 재니 숫자가 완전히 달라졌다.

| 템플릿 | 콜드 → 웜 | 템플릿 | 콜드 → 웜 |
|---|---|---|---|
| `root_cause_from_incident` | **636ms** → 36ms | `similar_case` | 311ms → 42ms |
| `root_cause_from_change` | 510ms → 39ms | `change_timeline` | 321ms → 40ms |
| `root_cause_from_sr` | 450ms → 40ms | `default_enrichment` | 222ms → 38ms |
| `root_cause_from_release` | 433ms → 50ms | `sr_vec` / `chunk_vec` | 291→51ms / 179→49ms |

**플랜 컴파일 비용이 실행 자체보다 6~16배 크다.**

Neo4j는 쿼리 문자열마다 플랜을 따로 컴파일해 캐시한다.
우리 템플릿은 7개고, 서로 다른 문자열이니 **서로의 캐시를 나눠 쓰지도 않는다.**
게다가 위 수치는 이미 한참 떠 있던 서버에서 잰 값이다.
접속 직후처럼 더 차가운 상태에서는 이게 1초를 넘겨 예산을 그대로 깬다.

여기서 좀 아찔했던 건 이 문장이었다.

> **배포 직후 첫 요청이 실패한다는 뜻이다. 그리고 데모에서 첫 질의가 그 요청이다.**

심사위원 앞에서 처음 누르는 버튼이 정확히 이 경로다.
운 좋게 통합 테스트를 차가운 상태에서 돌려봤으니 나왔지, 아니었으면 당일에 봤을 것이다.

### 예산이 재는 시간과 사용자가 겪는 시간이 다르다

정리하면 이렇다.

```
질의 예산 1,000ms  ←  "쿼리 실행이 이 안에 끝나야 한다"고 정한 값
첫 질의 실제       =  플랜 컴파일 + 실행
```

예산을 잡을 때 나는 **실행 시간만 생각하고 있었다.**
그런데 타임아웃은 컴파일까지 포함해서 걸린다.
성능 예산을 정할 때 "무엇에 대한 예산인지"를 확인하지 않으면
평상시엔 여유롭고 **딱 한 번, 가장 중요한 순간에만** 깨진다.

## 2. 트래픽을 받기 전에 채운다

고친 방식은 단순하다. lifespan에서 `warm_up()`을 부르고,
등록된 템플릿을 **존재하지 않는 앵커**로 한 번씩 실행한다.

```python
WARMUP_ANCHOR_ID = "__retriever_warmup__"   # 어느 원장 형식과도 겹치지 않는다

async def warm_up(self, *, timeout_ms: int) -> None:
    await asyncio.gather(
        *(self._warm_template(policy, timeout_ms) for policy in registered_policies())
    )
```

없는 ID를 써도 되는 이유가 이번에 배운 것 중 제일 재밌었다.

> **플랜 캐시의 키는 파라미터 값이 아니라 쿼리 문자열이다.**

그래서 결과가 0건으로 끝나도 플랜은 그대로 남고, 첫 실제 질의가 그걸 재사용한다.
워밍 후 첫 실제 질의는 29~264ms(미워밍 222~636ms).

`EXPLAIN`으로 워밍하는 방법도 재봤는데 68~222ms로 **덜 채운다.**
파싱과 논리 계획까지만 공유되고 실행 가능한 형태는 다시 만드는 것으로 보인다.
실제로 한 번 돌리는 쪽이 확실하다.

### 결정 네 가지

**① 워밍에는 질의 예산을 쓰지 않는다**

```python
neo4j_warmup_timeout_ms: int = Field(default=5_000, ge=0)   # 질의 예산은 1,000ms
```

같은 1초를 걸면 워밍 자체가 타임아웃으로 끝나 아무것도 못 채운다.
**컴파일이 그 1초를 넘기는 게 애초에 이 워밍을 넣은 이유다.**
자기가 해결하려는 문제로 자기가 죽는 설정이 될 뻔했다. `0`이면 워밍하지 않는다.

**② 벡터 검색은 합성 단위 벡터로 워밍한다**

```python
def warmup_vector(dimension: int) -> list[float]:
    return [1.0] + [0.0] * (dimension - 1)
```

임베딩 제공자를 부르면 기동 경로에 Azure 왕복이 하나 더 붙는다.
그러면 워밍이 실패했을 때 **원인이 Neo4j인지 Azure인지 구분되지 않는다.**
영벡터를 안 쓴 건 코사인 유사도에서 0으로 나누기 때문이다.

테스트에는 아예 이런 걸 뒀다.

```python
class ExplodingEmbedding:
    """워밍이 임베딩 제공자를 부르면 즉시 드러나게 한다."""
    async def embed(self, text: str) -> list[float]:
        raise AssertionError("워밍은 임베딩 제공자를 불러서는 안 된다")
```

"부르지 않는다"는 의도는 주석으로 적으면 다음 사람이 지나간다.
**터지게 만들면 안 지나간다.**

**③ 워밍 실패는 기동을 막지 않는다**

Neo4j가 아직 안 떠 있다고 앱을 죽이면,
**준비 상태를 보고할 주체까지 같이 사라진다.** 그 판단은 `/ready`가 한다.

그렇다고 조용히 넘기지도 않는다. 실패한 제공자 이름을 돌려주고 경고를 남긴다.

```python
logger.warning("warm-up failed for %s; the first query will pay for it", name)
```

워밍이 빠진 채 뜬 인스턴스는 첫 질의가 타임아웃으로 떨어진다.
그때 "왜?"의 답이 로그에 있어야 한다.

**④ 검색 쿼리를 모듈 상수로 올렸다**

이건 리팩터링처럼 보이지만 아니다. **정합성 문제다.**
플랜 캐시 키가 쿼리 문자열이므로, 검색과 워밍이 **같은 상수**를 봐야 한다.
공백 한 칸만 달라도 워밍은 엉뚱한 항목을 채우고
첫 질의는 컴파일 비용을 그대로 문다. 그러고도 로그에는 아무것도 안 남는다.

추출 전후 문자열이 바이트 단위로 동일한지 확인했다(717자·551자).

## 3. 그래프가 죽으면 답변이 한 건도 안 나가던 것

두 번째 건은 성격이 다르다. P0-9에서 "관찰 하나"로 넘겨뒀던 항목이다.

`SIMILAR_CASE` 답변의 `조치` 절 검증이 출처의 노드 유형을
`evidence_paths`에서**만** 찾고 있었다.

```python
if source_id not in source_nodes:   # 경로가 비면 항상 참
    ...                             # → 조치 문장 전부 미확인
```

### 왜 이게 문제인가

유사 사례 후보는 **그래프에서만 오지 않는다.**
Azure Hybrid·RDB Keyword·Neo4j Vector에서도 오고,
그 출처는 경로가 아니라 후보 레지스트리에 실린다.

```
그래프 제공자 장애
  → 검색은 멀쩡히 SR 을 찾아온다
  → 그런데 답변은 한 건도 검증을 통과하지 못한다
  → PARTIAL 로 답할 수 있는 상황에서 폴백으로 밀려난다
```

폴백은 "근거가 부족합니다"에 해당하는 답이다.
근거는 있는데 **근거를 어디서 찾을지를 한 곳으로만 정해둔 탓에** 없다고 답하고 있었다.

고친 건 한 줄 수준이다. 경로에 없으면 `sources`의 `SourceRef.type`도 같이 본다.

### 완화는 SR까지만

여기서 멈춘 게 중요하다. 답변(`:답변포함`)은 **그대로 경로를 요구한다.**

```python
if source_type == "SR":
    return True
# 답변은 그 SR 에 실제로 걸린 것만 인용할 수 있다
return source_type == "ANSWER" and node is not None and node.id in linked_answer_ids
```

"이게 답변이다"는 유형만 봐도 알 수 있지만,
**"이 SR에 달린 답변이다"는 경로로만 확인된다.**
유형만 보고 통과시키면 남의 SR에 달린 답변을 이 사례의 조치라고 제시할 수 있게 된다.
P0-8에서 "SR 또는 연결된 답변 출처만 허용"이 지키려던 게 정확히 이쪽이었다.

같은 모양의 `CHANGE_TIMELINE`은 손대지 않았다.
타임라인 문장은 시각 속성을 가진 노드가 근거라 경로 없이 검증할 방법이 없다.
**거기서는 거부가 맞다.**

> 완화할 수 있는 검증과 완화하면 안 되는 검증이 같은 코드 모양을 하고 있다.
> 모양이 같다고 같이 고치면, 보안 검증 하나가 조용히 사라진다.

## 어제의 정리

| 배운 것 | 한 줄 요약 |
|---|---|
| 재현 조건 | "가끔 실패"가 아니라 "차가울 때 실패"였다. 조건을 찾으면 간헐이 아니다 |
| 성능 예산 | 무엇에 대한 예산인지 확인하지 않으면 가장 중요한 한 번만 깨진다 |
| 캐시 키 | 플랜 캐시는 파라미터가 아니라 쿼리 문자열로 잡힌다 |
| 워밍 상한 | 해결하려는 문제와 같은 값을 걸면 워밍이 그 문제로 죽는다 |
| 기동 실패 | 앱이 죽으면 준비 상태를 보고할 주체까지 사라진다 |
| 의도 표현 | "부르면 안 된다"는 주석 말고 터지는 테스트로 |
| 근거 탐색 | 근거가 오는 경로가 여럿이면 검증도 그만큼 봐야 한다 |
| 완화 범위 | 코드 모양이 같다고 같이 완화하면 보안 검증이 조용히 사라진다 |

가장 크게 남은 건 이거다.

> **평상시에 잘 도는 것과 처음에 잘 도는 것은 다른 문제다.**
> 그리고 데모에서 사람들이 보는 건 언제나 첫 번째다.

지난 글에서 "실제 그래프가 어떻게 생겼는지 아는 것"이 먼저라고 썼는데,
어제 하나 더 붙었다. **"실제로 처음 켰을 때 어떻게 되는지"도 봐야 한다.**
켜둔 채로 개발하면 첫 실행 경로는 하루에 한 번도 안 지나간다.

## 검증 상태와 남은 것

정직하게 적어두면 이렇다.

```
오프라인   293 passed / 28 skipped   (기준선 280 → 290 → 293, 회귀 없음)
ruff       check · format 양쪽 통과
실 Neo4j   19 passed  ← 단, 쿼리 상수 추출 "직전" 값
```

마지막 줄이 걸린다. 상수를 추출한 **직후** 재확인을 하려는데 VM 접속이 끊겼다.
문자열이 바이트 단위로 동일한 건 확인했지만,
**바이트가 같다는 확인과 실제로 도는 걸 본 것은 다르다.**
플랜 캐시 얘기를 한바탕 하고 나서 이걸 남겨두는 건 좀 그래서, 다음 접속 때 제일 먼저 볼 생각이다.

다음에 할 것.

- 상수 추출 직후 실 Neo4j 재검증 (VM 재접속 즉시)
- 워밍 실제 효과를 배포 환경에서 한 번 더 — 지금 수치는 전부 개발 접속 기준이다
- `skc` → `csy` → `main` 병합. 통과분을 팀 공용으로 올려야 한다
- 항공 도메인 질의를 같은 멀티홉 경로로 통과시키기

플랜 캐시 워밍은 아마 Neo4j 운영하는 곳이면 다 하는 일일 텐데,
나는 타임아웃 로그를 하루 들여다보고 나서야 알았다.
DB마다 "처음 한 번"에 무슨 값을 치르는지 정도는 미리 알아두는 게 맞겠다는 생각이 들었다.
